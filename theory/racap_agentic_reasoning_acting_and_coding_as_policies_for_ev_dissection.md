这篇解决什么问题？CaP 方法让机器人"现场写 Python 程序"来干活，但一次代码迭代要 6.8–23.8 秒（多轮试错 60.8–113.6 秒），而且一个程序里既混着"可复用的抓取/接触几何"，又混着"这次任务专用的坐标和抓取高度"——换个任务就得重写。

## 1. 核心架构/方法总览 (Overview / Architecture)

### 1.1 系统对比概览 (System Component Comparison)

RACaP 把可部署策略写成三件套：`Π = (A_θ, π_φ, M)`——Policy API 库、ReAct 策略（harness 参数）、长期经验记忆。三者在**部署前演化、部署时冻结**。

| 模块 | 输入 | 输出 | 何时更新 | 部署时是否冻结 |
|------|------|------|----------|----------------|
| Policy API 库 `A_θ` | 结构化参数（pick/place/yaw/grasp type/clearance/contact mode…） | 状态报告 + 物理测量 + 新 RGB-D 图 | 演化期（candidate 替换 parent） | ✅ 冻结 |
| ReAct harness `π_φ` | 指令 + RGB-D + 工具报告 + 工作记忆 + 检索到的经验 | 结构化 JSON：选哪个 tool、传什么参数 | 演化期（phase 2 self-play） | ✅ 冻结（只改调用） |
| 工作记忆（episode 级） | 当前指令、剩余子目标、近期 API 调用、视觉结果 | 决策上下文 | **每个 episode 重置、运行时更新** | ❌ 运行时活跃 |
| 长期经验记忆 `M` | 过往失败的通用教训（不含坐标/答案） | 检索到的可复用先验 | 演化期 | ✅ 冻结 |
| 演化 harness | rollout 分析、候选代码生成、paired 回归测试 | 晋升/淘汰决策 | 演化期 | 不存在于部署 |

关键区别：CaP / CaP-X / RATS 在**执行期**生成或修复源码；RACaP 在**执行期绝不生成、编译、修复 Python**（论文 §3.5 明确声明），只允许 ReAct 改 API 参数。

### 1.2 关键机制 (Key Mechanism)

- **演化-执行解耦（evolution-to-execution）**：把"物理机制"（抓取几何、接触控制、插入/堆叠/关节操作）沉淀进 API；把"场景相关决策"（动作顺序、参数、恢复、停机）留给运行时。
- **两阶段演化**：Phase 1 用能力课程（S0→S6）先建立可诊断的最低能力；Phase 2 才让 harness 自主聚类失败、提改动、做 paired 验证。动机很实在：从零开始自我演化时，一次失败可能同时混了感知/抓取/放置/路由/停机错误，coding agent 归因不了，容易陷入局部最优（论文明确写了这个 motivating failure）。
- **Paired 验证而非单次 rollout**：候选代码在**相同任务、种子、预算**下与冻结的 parent 对比，只有严格更高的 native success 才替换（Eq. 2），平局与回归都归档。这是防过拟合的关键。
- **两层 ReAct 而非六个 agent**：Full ReAct 解析整条指令、排序子目标、路由 6 个 API；Transport ReAct 是子控制器，专管"单次取-放"局部循环。
- **可 steerability 的接口设计**：API 暴露 typed 参数（如 `contact_strategy`、`amount`、`nudge`），让 ReAct 在不改源码的前提下适配新场景。

⚡ **Eureka Moment**：**"代码不该在运行时写，而该在演化期写完之后冻结；运行时唯一要动的是函数参数。"**——把"可复用机制"与"任务特定决策"沿时间轴切开，同时收获泛化性（机制跨任务）与可 steerability（参数随场景变）。

## 2. 数学核心 (Math Core)

📌 **Napkin Formula**（一行抓住本质）：

```
θ* = argmax_θ'  Σ_{τ∈D_dev} [ S(τ; A_θ', π_φ, M) − S(τ; A_θ, π_φ, M) ]
     （固定 π_φ、M，只用「配对增益」选 API 版本；只改代码，不碰运行时决策）
```

**目标**：在固定运行时 ReAct 与记忆的前提下，从候选 API 实现中选出**跨任务净增益**最大者，而不是在单条 rollout 上刷分。

**公式（Eq. 2，论文 §3.1）**：

```
θ* = argmax_θ'  Σ_{τ∈D_dev} [ S(τ, A_θ', π_φ, M) − S(τ, A_θ, π_φ, M) ]
```

**公式（Eq. 3，固定 API、选 ReAct harness 与记忆，字典序目标）**：

```
(φ*, M*) = lex-argmax_{φ', M'} ( Σ_τ S(τ, A_θ*, π_φ', M') ,  −Σ_τ T(τ, A_θ*, π_φ', M') )
```

**变量说明**：

| 符号 | 含义 |
|------|------|
| `τ` | 一个操作任务（含隐藏的 evaluator goal） |
| `x` | 语言指令 |
| `o_t` | 时刻 t 观测：RGB-D、机器人状态、历史工具报告 |
| `A_θ` | Policy API 库，`θ` 为实现参数 |
| `π_φ` | 运行时 ReAct 策略，`φ` 为 harness 参数 |
| `M` | 长期经验记忆（不含任务答案/绝对坐标） |
| `S(τ, ·) ∈ {0,1}` | 该任务上的 native（仿真器谓词）成功 |
| `T(τ, ·)` | 该任务的 ReAct 轮数 |
| `D_dev` | 开发集（LIBERO-90） |

**直觉**：Eq. 2 是一个**配对差（paired gain）**最大化——只有当一个机制改动在**同一批任务/种子**上"赚的比亏的多"时才被接纳，天然抑制过拟合到个别 rollout。Eq. 3 是**字典序**：先比成功率，成功率打平才比轮数——防止"更快但更差"的 agent 胜出。

> 符号与本文保持一致：`A_θ` 为 Policy API 库（非 action space），`θ` 为代码实现参数，`φ` 为 prompt/harness 参数。所有公式均以代码块表达，避免 LaTeX 渲染问题。

## 3. 带数字走一遍：玩具例子 (Worked Example)

用 Eq. 2 走一遍"是否晋升一个 API 候选"（数值为便于说明的假设）：

设开发集 `D_dev = {τ1, τ2, τ3}`，parent `θ` 与候选 `θ'` 的成功情况：

| 任务 | parent S(τ;θ) | 候选 S(τ;θ') | 差 |
|------|---------------|--------------|-----|
| τ1 抓取几何 | 1 | 1 | 0 |
| τ2 插入 | 0 | 1 | **+1** |
| τ3 长程顺序 | 1 | 0 | **−1** |
| 合计 | 2 | 2 | **0** |

按 Eq. 2，净增益 = 0 ⇒ **不晋升**（论文规则：必须严格为正，平局归档）。这一条就挡住了"为了修 τ2 而牺牲 τ3"的假改进——CaP 类系统若不配对对比，很容易被这种此消彼长骗过。

再看 Phase 2 真实账本（论文 §3.4）：596 个开发 episode → 生成 **32** 个提案 → 仿真测试 **23** 个候选 → **9** 个被晋升。in-domain 只从 48/90（53.3%）涨到 49/90（54.4%，**只多 1 个任务**），但零样本 LIBERO-PRO 从 32.8% → **45.0%**、LIBERO-Long 从 32.0% → **46.0%**、PRO 中位策略时间 454s → **380s**。

这就是本文最反直觉的一点：**in-domain 几乎没涨，泛化却暴涨**——因为晋升标准奖励的是"跨任务可复用机制"，而不是对训练分布的记忆。

## 4. 工程视角 (Engineering View)

把公式落到控制频率、模块边界、部署约束：

| 工程指标 | RACaP | CaP-X | RATS-90 | 含义 |
|----------|-------|-------|---------|------|
| 运行时是否写代码 | ❌ 冻结 | ✅ 生成/修复 | ✅ 生成/修复 | RACaP 消灭了运行时代码迭代的延迟源 |
| 单次代码迭代耗时 | — | 6.8–23.8 s | — | CaP 家族的固定延迟税 |
| 多轮试错耗时 | — | 60.8–113.6 s | — | 物理执行中"边跑边修"的抖动来源 |
| PRO 中位策略时间 | **380 s** | 845 s | 954 s | RACaP 约 1.9× 快于最强 CaP 基线 |
| PRO 平均 API 调用 | 15.9 | 13.0 | 45.2 | 调用少 ≠ 快：CaP-X 调用少但每步更贵 |
| ReAct 单步延迟（蒸馏后） | **0.750 s** | — | — | vs 托管教师 9.895 s，13.2× 加速 |

- **延迟结构**：RACaP 把"代码推理"整体移出执行路径后，运行时只剩"VLM 决策 + 冻结 API 调用"。蒸馏把单步决策从 ~9.9s 压到 0.75s，重复物理调用从 16 次降到 4 次——这对"观测→动作"延迟敏感的真机部署是硬收益。
- **模块边界**：论文附录 A 的责任边界表很值得抄——Policy API 拥有"局部接触几何 + 运动执行 + 物理测量 + 失败报告"，**排除**整任务指令/因果排序/语义状态检查；ReAct 拥有"任务分解 + 工具与参数选择 + 恢复 + 停机"，**排除**源码修改/特权评测状态。边界一旦 typed 化，就能被回归测试保护。
- **抖动/失稳教训**：RATS-90 因"保存的 helper 函数"与"新生成的 caller 脚本"接口漂移（键名不匹配、数组格式意外、参数未处理），成功率不升反降（17.8%→8.3%），321 次失败中 181 次归因于此。**没有 typed interface 的自改进会反噬**——这是本文给工程界最硬的警告。
- **部署约束**：每个执行回合输出 schema 检查过的调用记录（参数、报告、模型身份、延迟、token、成本）；工作记忆每 episode 重置，仅通过公共观测与工具报告更新。

## 6. 能力与失败模式 (Capabilities & Failure Modes)

**能做**：
- 在教育类长程任务（LIBERO-Long）上把成功率从 CaP 基线的 2.0–4.0% 拉到 46.0%，增益集中在 `On`（40%→65%）与 `Turnon`（20%→50%）。
- 零样本跨扰动迁移（物体位置/目标改写），且**运行时零代码生成**。
- 通过一次性校准卡（one-trial card）快速适配新任务族。

**不能做 / 弱在哪**：
- `Close` 谓词始终 **0.0%**——作者如实列出，未解决。
- 长程增益来自"完成更复杂的子目标序列"（平均 ReAct 轮数从 8.22 升到 8.72），不是"更短的决策轨迹"；McNemar p=0.118，**统计上不显著**。
- 七物体基准无人完成全部 7 个。
- **跨本体（Robosuite）零样本很弱**：冻结 Phase 2 只 17.1%（CaP-X 25.7%），必须做域演化才能到 31.4%；论文明确说 typed interface 促成的是"高效目标域适配"，而非"直接零样本跨本体"。
- **冻结源码的代价**：只能泛化到 Policy API 闭包内，无法在线发明新物理技能（论文 §5 自认）。

### 6.1 隐含假设 (Hidden Assumptions)

- **"evaluator goal 隐藏"但信号可得**：演化期用 native success 作晋升判据，这需要仿真器谓词可用；真机上"成功信号"从哪来、噪声多大，未展开。
- **LIBERO-90 只跑 seed 0**：作者理由是任务数足够，但 in-domain 结论（54.4%）方差未被充分刻画。
- **托管模型能力是前提**：演化期依赖 GPT-5.6 级 coding agent，评测期 GPT-5.5；若换更弱模型，coding agent 能否提出有效机制改动是开放问题。
- **"可复用机制"与"任务特定决策"真的可切**：接口设计（typed 参数）需要人工定义参数空间（grasp type/clearance/contact mode…），切分质量本身依赖领域知识。
- **经验记忆不含特权信息**：作者声明 M 不存任务答案/绝对坐标，但如何审计"通用教训"与"隐性过拟合"的边界，未给定量指标。

| **RACaP（本文）** | **演化-执行解耦** | **typed Policy API + 双 ReAct + 记忆** | **课程学习 + 配对自演化（32 提案→23 测试→9 晋升）** | **长程操作 + 零样本迁移 + 高效真机部署** | **❌ 冻结** |

**面试 Tip**：被问到"RACaP 和 RATS 差在哪"时，一句话答——**"RATS 用好玩（novelty/learnability）当目标在线攒代码，目标跟下游任务不对齐，接口还会漂移；RACaP 把代码冻结成 typed API，用配对净增益（Eq.2）当晋升标准，只在演化期改代码、运行时只改参数。"**

## 8. 精讀建議 (Reading Guide)

- **值得精讀原文的人**：
  1. 做 agentic robot / CaP 路线、想把"自改进"落成可部署堆栈的研究者/工程师；
  2. 设计具身 agent harness、关心"演化期 vs 执行期"接口边界的系统工程师；
  3. 评估"托管大模型 + 蒸馏小模型"做真机实时决策可行性的落地团队。
- **建議章節路徑**：先讀 §3.1（问题设定 + Eq.2/3）→ 再看 §3.3–3.5（两阶段演化 + 冻结运行时三件套）→ 附录 A 表 2（责任边界表，最实用）→ §4.2 表 1 与 §3.6（数字与蒸馏）→ §5 Limitations。可跳附录 C 的定性 trace（示例而已）、D 的资源审计（除非你要复现成本）。
- **不值得精讀的理由**：如果你不做机器人操作、或已熟悉 CaP/RATS/ASPIRE 这一支且只关心端到端 VLA 模型，读摘要 + 本笔记的 §1.1/§2 即可。若你不做仿真且真机成功信号难获取，本文的演化机制迁移价值有限。
