## 1. 核心架構/方法總覽 (Overview / Architecture)

论文有三大块：**动作对齐（Action Alignment）**、**视觉对齐（Visual Alignment）**、**VLA 后训练**。

### 1.2 关键机制 (Key Mechanism)

- **为什么用固定追踪器（SONIC）**：不在每个任务上重训控制器，让控制器成为"共享底座"，对齐工作全部放在**离线参考修正**上，跨任务复用。
- **为什么要「粗+细」两段**：单纯追踪人类参考会留下很大末端误差（Table 1：H 阶段 11.21 cm）；但**在线 IK 修正会破坏全身协调**（作者实测三种在线 IK 都导致 SONIC rollout 摔倒），所以改在离线做。
- **为什么视觉也要对齐**：动作对齐只解决"做什么动作"，解决不了"从什么视角看到什么"。人类手臂 vs 机器人手臂、相机视角差会拖累策略（Table 4：仅动作对齐不够）。

⚡ **Eureka Moment**：**不要把人类动作"retarget 成机器人动作"，而要"让机器人追踪器先跑一遍，再离线把这遍 rollout 掰向人类交互目标"**——修正的是*参考*，而不是覆盖协同控制器输出，从而在提高末端精度的同时保住全身协调。

## 2. 數學核心 (Math Core)

📌 **Napkin Formula**（一行抓住本质）：

```
在线重定向破坏协调 → 改为离线：先追踪器 rollout，再用 MLP 响应模型预测「动一点关节 → 末端动多少」，
迭代把预测响应掰到残余误差上： min_z  || R_ψ(J·Δu(z)) − r^k ||²
```

**目标**：在保持全身协调的前提下，提升末端（手掌/脚掌）位姿精度。

**训练接口（式 1）**：

```
o_t = ( Ĩ_t , q_t , ℓ )
a_t = ( z_t , h_t^L , h_t^R )
```

**追踪器编码（式 2）**：

```
z_{1:T}^0 = E_r( b_{1:T}^ref )
```

**细化阶段（式 3–4）**：

```
Δu(z)  = D_c(z, s^k) − D_c(z^k, s^k)      # 候选 token 相对当前 token 的关节命令变化
Δê(z)  = R_ψ( J^k · Δu(z) )               # 预测的末端执行变化
L_track(z) = || Δê(z) − r^k ||²           # 让预测响应补偿当前残余
```

**变量说明**：

| 符号 | 含义 |
|------|------|
| q_t | Unitree G1 状态，**43 维** |
| z_t | SONIC motion token，**64 维** |
| h_t^{L/R} | BrainCo Revo2 手部命令，**各 6 维** |
| b_t | 机器人关节轨迹，**29 维** |
| E_r | SONIC 机器人运动编码器 |
| D_c | SONIC 控制解码器（token → 关节命令） |
| J^k | 关节命令变化 → 末端运动学变化的雅可比 |
| R_ψ | MLP 响应模型（学习"运动学变化如何映射到执行变化"） |
| r^k | 当前 roll-out 的末端残余误差（位置 + 手目标的相对旋转向量） |
| s^k | 控制器观测历史（rollout 上下文） |

**直觉**：
- 式 2 把"修好的参考"重新塞回追踪器，保证参考本身是协调、可执行的。
- 式 3–4 的思路是"**在固定 rollout 上下文下**，问响应模型：我这样改 token，末端会往哪动？"——梯度只穿过响应模型和控制解码器（**不穿模拟器**），所以优化很便宜。
- 每轮更新后**重新 rollout 一次**，用新 rollout 提供残余和上下文，进入下一轮。最终从优化历史里选一个"经过验证"的序列用于策略训练（可能是早期的 H 或 H+K）。

> 符号与本文/相关文档保持一致：token 用 z、状态用 q、手命令用 h，与 SONIC / π0.5 术语对齐。

## 3. 帶數字走一遍：玩具例子 (Worked Example)

假设单任务「把右脚抬起把抽屉顶关上（Close Drawer）」，只关心脚掌位置：

```
初始 H：SONIC rollout 后脚掌位置误差 ≈ 9.18 cm（Table 3 单位响应基线）
   │
   ▼
K 阶段（离线 IK）：把脚掌参考掰向人类脚目标，
   位置误差从 11.21 cm（全任务均值 H）降到 4.45 cm（均值 K）
   │
   ▼
D 阶段（MLP 响应细化，8 轮）：
   第 1 轮：rollout 得残余 r^0（脚掌现在离目标还差多少）
   用 R_ψ(J·Δu(z)) 预测「改 token → 脚移动多少」，取能让预测响应 ≈ r^0 的 z
   第 2 轮：重新 rollout，得新的 r^1，再优化 …… 共 8 轮
   │
   ▼
Close Drawer 最终位置误差 5.80 cm（MLP）
```

关键对比：
- **光用 8 轮 D，不做 K** → 位置误差仍高达 8.40 cm，方向误差 16.40°（说明 K 给的参考很关键）。
- **1 次 K + 8 轮 D** → 位置 3.97 cm，方向从 16.46° 降到 8.08°。
- **重复 8 次 K** → 4.86 → 4.77 cm，几乎没用（K 只需一次）。
- **MLP 响应 vs 单位响应**（假定关节动 = 末端动）→ 手臂任务误差再降 0.13–0.17 cm；**脚部任务收益最大**（9.18 → 5.80 cm），因为脚部修正需要连带平衡调整，不能被简单线性假设吞掉。

## 4. 工程視角 (Engineering View)

| 维度 | 观察 | 工程含义 |
|------|------|----------|
| 追踪器部署 | SONIC 跨四任务用**同一 checkpoint**，实时执行 token | 控制器是共享底座，可独立升级，不随任务膨胀 |
| 对齐成本 | IK + 多轮 rollout 属离线 | 训练前一次性投入，换取部署时零遥操作 |
| 吞吐瓶颈 | 论文自述「IK 与重复 rollout 限制吞吐」 | 大规模数据流水线时是主要延迟来源 |
| 动作抖动/稳定性 | 对齐仍可能产生不稳定动作 | 需更强稳定性约束才能批量安全使用 |
| 推理接口一致 | 训练用渲染图，推理直接用机器人相机图 | 无需在部署端做任何视觉后处理，边界干净 |
| 分辨率/视角鲁棒 | 随机裁剪、小旋转、光度抖动 | 用数据增强兜住人类与机器人运动幅度不同的视角漂移 |

**工程含义小结**：这套方法的"贵"在**离线准备**、"便宜"在**在线采集**。适合"场景多、任务多、难以把遥操作系统搬到每个现场"的场景；不适合"要求极高成功率、且已有成熟遥操作管线"的场景。

## 6. 能力與失敗模式 (Capabilities & Failure Modes)

**能做**：
- 通过同一全身控制器监督**手部与脚部**操作（Close Drawer 证明脚部也吃得下）。
- 在**无目标任务机器人演示**下实现四个真实任务的零样本迁移。
- 用显著更低的人力达到与遥操作数据"相当但略低"的水平。

**不能做 / 失敗模式**：
- **绝对分数低**：均值 51.67%，单任务最低 38.33%（Open Fridge）。作者用"部分完成"计分，说明大量试验是部分成功。
- **在线 IK 直接崩**：三种在线 IK 实现都导致 SONIC rollout 不稳定（含摔倒），故被放弃。
- **对齐本身不稳定**：仍会产生不稳定动作；IK 与重复 rollout 限制吞吐。
- **泛化边界**：仅在 Unitree G1 + 四个桌面/室内任务上验证，不涉及移动、双臂协同大范围、人形长时程导航。
- **视觉收益任务相关**：合并渲染+增强最佳，但 Close Laptop 上**仅增强**更好——说明视觉对齐不是万能药。

### 6.1 隐含假设 (Hidden Assumptions)

- **摄像头对齐假设**：默认人类与机器人相机高度/角度相近即可，剩余差异用图像增强兜底——但运动幅度不同导致的视角漂移是否总能被增强覆盖，未系统验证。
- **目标位姿可迁移假设**：把人类手掌/脚掌当"任务目标"，默认人形机器人的可行交互几何与人类一致（例如把抽屉顶关所需的脚部姿态）。
- **固定追踪器足够假设**：整个框架建立在"SONIC 追踪器跨任务通用"之上；若换平台/换控制器，H/K/D 管线是否还成立未验证。
- **人力统计口径假设**：人力比较把 setup/校准/排错/重置都算入并摊薄共享开销，结论对"两个操作员 vs 一个操作员"的设定敏感。
