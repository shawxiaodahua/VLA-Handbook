### 1.2 关键机制 (Key Mechanism)

- **为什么这样设计**：作者先假设「敏感性是系统性的」，如果不是，规则无法跨任务迁移。因此 §IV 先用统计检验和 oracle 搜索证明：一个词的改动会造成**显著、可重复、成组出现**的成功率差。
- **证据如何变成规则**：LLM 看到的是「同一任务的多个措辞 + 各自成功率」，它要总结的是**跨任务成立**的措辞偏好，而非「这个任务该怎么说」。
- **规则为什么可读**：规则显式列出（如「plate 不要换成 dish」「onto 换成 on」），而不是训练一个隐式 rewriter。作者明确用「显式、人类可读」作为与 Jeong 等人学习式 language feedback policy 的区别。
- **每回合一次的设计动机**：与 CoVer 的逐步验证对比，作者想证明**只改语言**（不动动作）也能拿到主要收益，这样每步推理成本不变。

⚡ **Eureka Moment**：VLA 的语言敏感性并不表现为「每任务不同」，它更像**共享的令牌（token）偏好**——同一个词（如 hot plate、dish）在若干任务上造成一致损失（hot plate 在出现处失败，plate→dish 在 π_0/π_0.5 上分别损失 19/56 点），但也存在 purple 等不迁移的反例，因此规则只能捕捉统计上系统性的偏好，而不能覆盖所有情况。

## 2. 数学核心 (Math Core)

📌 **Napkin Formula**（一行抓住本质）：

```
目标：argmax_R  E_ℓ [ S_t( f_R(ℓ) ) ]     s.t.  π 不变，f_R 每回合调用一次,  R 在 sealed 集外固定
```

先把问题形式化。设 π 为冻结策略，ℓ 为指令，t 为任务，S_t(ℓ) 为成功率，ℓ_t 为任务的规范指令（canonical），L_t 为所有保留目标的合法改写。

**单编辑摆动（single-edit swing）**：

```
swing(ℓ, ℓ') = | S_t(ℓ) - S_t(ℓ') |,   ℓ 与 ℓ' 只差一处编辑
显著条件：两比例 z 检验 p < 0.05；π_0.5 另要求 |swing| ≥ 18 点
```

**Oracle headroom**（oracle 短语搜索给出的上界）：

```
H_t = max_{ℓ ∈ L_t} S_t(ℓ) - S_t(ℓ_t)
```

**规则书 R 与改写函数 f_R**：

```
f_R : (ℓ, R, trace) → ℓ'      （部署时每回合应用一次，之后不再改）
E_ℓ [ S_t( f_R(ℓ) ) ]  在「未贡献证据的任务」上评估
```

**评测统计量（配对）**：以「基础指令 i」为配对单位，

```
d_i = c_i - b_i   =  S_t( f_R(ℓ_i) ) - S_t( ℓ_i )        （同布局、同随机数）
p 值：对 mean(d_i) 做双侧符号翻转置换检验；SIMPLER 主比较用 20,000 次重采样，n ≤ 12 时精确枚举；LIBERO 复现用 n=200 bases 和 10,000 次置换
相对效应 = mean(d_i) / 基线合并率        （表 I、表 II 用的就是这一口径）
```

**代理分数（不可模拟任务）**：

```
proxy(ℓ) = mean_{τ 轨迹, k 帧} | a_hat_g(τ, k; ℓ) - a_g(τ, k) |_gripper
（gripper 维度、原始动作单位、对 chunk horizon 与 4 次解码取平均）
经验：434 任务–措辞对、15 任务变体上，proxy 与 rollout 成功率任务内 Pearson r = 0.54
```

> 符号与本文一致：S_t 是成功率，ℓ 是指令原文，ℓ' 是改写后指令，R 是规则书，f_R 是应用器，d_i 是配对差，n 是基础指令数（不是 rollout 数）。

**直觉**：
1. 成功率的差可以按「指令」对齐，而游戏（场景布局）差异用 common random numbers 消掉——所以 d_i 才是关键读数。
2. 「规则 R 在 sealed 任务上才有意义」意味着 R 不能被任何 sealed 任务的出现所污染；这是零样本评估的前提。
3. Oracle headroom 是**上界**而不是可达目标，它告诉你「如果措辞完美，还剩多少提升空间」。

## 3. 带数字走一遍：玩具例子 (Worked Example)

> ⚠️ 以下为**假设数值**，仅用于演示流水线的算术闭环；数值来自论文表 I/II 的实测量级，但「某个具体指令」的分解为本文作者的条件性推演，非论文实测。

假设有一条对抗措辞 `ℓ = "could you please put the carrot on the dish"`，冻结 π_0 在 24 个固定布局 × n=72 次 rollout 上的成功率 `S = 24.5%`。

**第 1 步：规则命中**

R 中含一条规则：「不要把常见名词换成兄弟词——保留 plate，不要 dish」。applier 把 `dish → plate`，得 `ℓ' = "put carrot on plate"`。

**第 2 步：实测的「兄弟词惩罚」**

论文 §IV-C 报告：π_0 上 `plate → dish` 约 **−19 点**，π_0.5 上约 **−56 点**。所以把方向反过来（dish → plate）的假设收益 ≈ +19 点（π_0）。

**第 3 步：按表 I 的工作量级验算**

表 I 报告的相对提升为 +26% 左右，基线 24.5%，平均配对差：

```
0.26 × 24.5% ≈ +6.4 个百分点
24.5% → 约 30.9%
```

而「dish → plate」单条规则在本假设里贡献的 19 点，**高于**整本规则书的均值 6.4 点——这不是矛盾：因为单任务单规则的 19 点只对含该词的指令生效，而表 I 的平均把大量不命中的指令稀释了。

**同法对 π_0.5 的数字走一遍**：

- 论文实测：π_0.5 在 LIBERO 上 93.6% → 97.8%（in-finetune，平均）。
- 拆解（论文 §VI-F 宣称）：`hot plate / hotplate / burner → stove` 约 +45 点，但只覆盖约 9/200 条测试指令；`dish → plate` 约 +24 点；`onto → on` 与 `into → in` 约 +2.5 点、覆盖约 50 条；`grab / lift → pick up` 约 +2.4 点、覆盖约 15 条。
- **验算量级**：45 × 9/200 + 24 × (少量) + 2.5 × 50/200 + 2.4 × 15/200 ≈ 2.0 + ~2 + 0.6 + 0.18 ≈ 4.8 点左右，与 93.6 → 97.8 的 4.2 点在量级上一致（差异来自覆盖数量估计不精细）。

**结论**：改写规则的本质是**把低命中率、高单位收益的「令牌修复」和大覆盖、小收益的「介词修复」组合起来**，而不是全局提升。

## 4. 工程视角 (Engineering View)

| 维度 | 数值/事实 | 工程含义 |
|------|-----------|----------|
| 每回合模型调用次数 | 2 次（trace + 改写） | 若控制频率是 5–10 Hz，改写开销相对一个 episode 的总时长可忽略；但 episode 极短（< 3s）时改写比本体还贵 |
| 延迟 | trace ≈ 2.5s；Claude 改写 ≈ 10s；Gemini ≈ 17s；本地 Qwen ≈ 1–2s | **本地 Qwen 是唯一能嵌入控制回路的选项**；Claude/Gemini 属于「离线批处理」 |
| 改写复用 | 一次改写跨所有布局与重复复用 | 同一指令在评测时多次复用，可不摊薄单次成本，但会**放大**改写错误的后果 |
| 逐步验证 vs 一次性 | CoVer 每步 40 个候选（8 改写 × 5 动作） | 本方法在推理成本上是 O(1)/episode，CoVer 是 O(steps × 40) |
| 策略权重 | 完全冻结 | 可用于已经在产线部署、**不希望你碰权重**的 VLA |
| 失败风险 | 改写输出会直接送到 VLA，无二次校验 | 若改写器幻觉或删掉关键物体，VLA 会执行错误任务——这是与「逐步验证」类方法最大的工程差异 |
| 依赖 | 外部 LLM（Claude / Gemini / Qwen） | 需要控制上下文的隐私与合规；论文未给成本分析 |

**工程含义一句话**：这套方法适合「回合制、长 episode、且改写器可放到本地小模型」的部署；不适合高频闭环控制（> 10 Hz）和「一次错误改写就灾难」的场景。

## 6. 能力与失败模式 (Capabilities & Failure Modes)

**能做什么**

| 能力 | 实测证据 | 条件 |
|------|----------|------|
| 跨 applier 稳定提升 | 表 I：Claude / Gemini / Qwen 三个应用器，相对提升 16.1–26.5% | 12 个 sealed SIMPLER 任务、π_0 |
| 增益集中于 out-of-distribution | 图 8：thin flanks 显示提升集中在 7 个 OOD 任务 | 同上 |
| 提升超越「仅改写」 | 表 II：对抗集 +23–29% 相对 no-rules rephraser | 规则贡献超出改写本身 |
| 迁移到另一个 VLA | π_0.5 + LIBERO：in-finetune 93.6 → 97.8% | p ≤ 0.005 |
| 与逐步验证方法对比占优 | 表 III：CoVer 在对抗集 21.6 vs no-rephraser 24.5 vs no-rules 24.3 | 同一 Gemini trace，公平比较 |

**不能做什么 / 失败模式**

1. **out-of-finetune 的 LIBERO 收益不显著**（p > 0.4）。作者自己承认，当策略本来就不怎么「看」指令时，改写无收益——这与 LIBERO-Plus/LIBERO-PRO 结论一致（策略可能忽略指令）。
2. **π_0.5 的对抗措辞在 in-finetune 上损失 50 点（97→47），在 out-of-finetune 上三档无差别（52/50/48）**。说明微调后的策略只在训练见过的地方才「读指令」。
3. **颜色修饰词无稳定符号**：加 “purple” 在一个任务 +61，在另一个任务 −30。**单条静态规则无法同时满足两者**——这是方法层面的硬约束。
4. **in-finetune 规则书表现较弱**：作者怀疑是 gripper error 代理分数弱，但未给出根因。
5. **canonical 集统计功效不足**（每任务仅 1 条短语，n=12），作者明确要求「谨慎解读」。
6. **改写错误无二次校验**：重写直接进 VLA，无 verifier。CoVer 的逐步验证恰好在这一点上补位。
7. **仅在两个 VLA、仅仿真**——作者自己列为下一步。

### 6.1 隐含假设 (Hidden Assumptions)

- **「规则跨任务成立」的假设**：方法的核心前提是敏感性系统性；论文自己也承认一个反例（purple 在任务间符号相反）。这说明系统性是**统计学意义**而非**逻辑必然**。
- **「sealed 任务不泄漏」的假设**：sealed 划分在任何 rulebook 证据生成前数周已固定，且只有非 sealed 任务进入蒸馏证据库；词汇分布是否重叠与任务是否进入证据库是不同问题，不能混为一谈。
- **「一次改写即可」的假设**：改写后不再改，假设单一改写点是最优决策点；论文未做「逐步改写」的消融。
- **「代理与 rollout 相关」的假设**：Pearson r = 0.54 只在 15 个任务变体上测过；这一相关性是否在其它任务族成立，论文未验证。
- **「无 multiple-comparison 校正」**：论文明确写出：π_0.5 的 426 个候选对中，约 21 个显著摆动可由偶然解释（期望值，未做多重比较校正）；π_0.5 最终清单经人工移除场景歧义后为 15 个集，π_0 为 26 个集，不能据此断言最终清单里有 21 个假阳性。

## 7. 与相关工作对比 (Comparison)

| 方法 | 是否改权重 | 干预粒度 | 是否需逐任务交互 | 能否零样本迁移 | 与本文最关键的差异 |
|------|------------|----------|-------------------|----------------|---------------------|
| 复述增强微调 [1,2,3] | 是 | 训练时 | 否 | 部分 | 本文研究**增强之后剩下的**敏感性 |
| CoVer [1] | 否 | **每控制步**，40 候选 | 否 | 部分 | 本文只改指令、不改动作、每回合一次，推理成本 O(1) |
| RoboMonkey [4] | 否 | 每步验证 | 否 | 部分 | 同上 |
| SARL [5] | 否 | 每任务在线 RL 搜索 prompt | **是** | 否（逐任务） | 本文规则固定、离线蒸馏、零样本 |
| VLA Grounder [6] | 否 | 每任务训练指令→命令翻译器 | 是 | 否 | 同上 |
| PALO [7] | 否 | 每任务分解搜索 | 是 | 否 | 同上 |
| Jeong et al. [16] | 否 | 学习式 language feedback policy | 否 | 部分 | 本文规则**显式、人类可读**、离线一次 |
| Hi Robot [19] | 是（上层 VLM） | 上层决定**发什么指令** | 否 | 是 | 本文学的是「**这种措辞**执行器是否可靠」，而非「**该做什么**」 |
| **本文** | **否** | **每回合一次改写** | **否** | **是** | 规则显式、蒸馏自 rollout、固定后零样本 |

**面试 Tip**：被问「VLA 语言敏感性能怎么修」时，一句话回答——「不改权重、不逐步验证，每回合把指令按离线蒸馏的显式规则改写一次；关键是先证明敏感性是系统性的，否则规则无法跨任务。」

## 8. 精讀建議 (Reading Guide)

- **值得精讀原文的人**：
  1. 正在做 VLA 指令鲁棒性、语言泛化评测的研究者；
  2. 需要给已部署 VLA 加「前置语言层」但不希望碰权重的工程团队；
  3. 想对比「逐步验证 vs 一次性改写」推理成本的研究者。

- **建議章節路徑**：
  - 先读 §IV（敏感性刻画）——这是全文论证基础；
  - 再看 §V–VI（规则蒸馏与主结果），重点看表 I/II 的效应量与 p 值；
  - §VI-F（π_0.5 复现）可挑读，因为 out-of-finetune 部分不显著，信息量有限；
  - §VII（结论与未来工作）最后一页即可，作者诚实列出局限。

- **不值得精讀的理由**：若你不做机器人学习、或已熟悉「推理时指令改写」这一套路，且对「显式规则 vs 学习式策略」的取舍不敏感，读摘要 + 表 I/II 即可。
