## 1. 核心架构/方法总览

### 1.1 系统对比概览

| 冻结 4B VLM（DM0.5，34 层） | 指令 L + 初始多视角 I₀ | 每层 (K₀ˡ, V₀ˡ) | **每 episode 1 次** | 冻结 |

论文自报参数量：RoboTwin 272.0M、LIBERO 184.7M 可训练参数（Table 10），即控制回路里跑的是"两亿级"而非"四十亿级"。

### 1.2 关键机制

- **记忆保留全部 34 层**，而不是只取最后一层。作者的解释是让 actor 能在不同 VLM 深度上检索任务上下文；Table 5 的对照给出代价：仅最后一层在 LIBERO 上 94.70 / 73.70，全 34 层 95.95 / 79.11。
- **查询按"未来时间步 × 手臂"索引**：τ ∈ {0,…,49}，a ∈ {left, right}，每个查询代表一条手臂的一个未来时刻，因此一次前向就能并行吐出整块动作，无需迭代去噪。
- **反馈在每个 chunk 边界重新注入**：同一份固定记忆，被不同的实时观测反复读取，这是"记忆固定但策略仍闭环"的关键。
- **KV memory adapter 用可学习打分混合 34 层**，并先用 rotary 变换把各层 key 对齐到共同空间再做加权和，避免直接相加不同深度表示的错位。
- **训练期离线预计算记忆**：VLM 冻结，所以 KV 缓存可离线算好并复用，训练时不必反复前向 4B 模型。

⚡ **Eureka Moment**：任务语义是 episode 级的慢变量、机器人状态是 chunk 级的快变量——把慢变量一次性烧进冻结的 KV 缓存，控制回路里就只剩下"检索"这个动作，而检索的算力比重新推理低一个数量级。

## 2. 数学核心

📌 **Napkin Formula**

```
摊薄延迟 = (T_prefill + ⌈H/K⌉ · T_actor) / H
```

这一行就是全文的经济学：prefill 是每 episode 的固定成本，被 episode 长度 H 摊薄；actor 调用次数随 H/K 线性增长。作者赌的是 T_prefill ≪ H·T_VLM_repeat。

**两阶段形式化**

```
M₀ = G_VLM(L, I₀)
Zₜ = G_online(Iₜ, Hₜ, qₜ)
Â_{t:t+K-1} = F_pred(Zₜ; M₀)
M₀ = {(K₀ˡ, V₀ˡ)}_{ℓ=1..34}
```

**查询初始化与记忆混合**

```
z_{τ,a}^{(0)} = e_time(τ) + e_arm(a),   τ ∈ {0,…,49}, a ∈ {left, right}
α_{m,ℓ} = softmax_ℓ(s_{m,ℓ})
(K̄ₘ, V̄ₘ) = Σ_{ℓ=1..34} α_{m,ℓ} · ( R_{c←ℓ}(K₀ˡ), V₀ˡ )
```

**训练目标（归一化动作上的 L1）**

```
L_act = (1/(K·D)) · Σ_{k=0}^{K-1} Σ_{d=1}^{D} | â_{t+k,d} − a_{t+k,d} |
```

| 符号 | 含义 |
|------|------|
| L, I₀ | 语言指令、episode 初始多视角帧 |
| T_prefill | 一次 VLM prefill 墙钟时间（RoboTwin 108.87 ms / LIBERO 88.38 ms） |
| T_actor | 一次 actor 调用墙钟时间（44.87 ms / 34.25 ms） |
| H | 该 episode 实际执行的环境步数 |
| K | action chunk 长度（RoboTwin 50 / LIBERO 10） |
| D | 单步动作维度（双臂合计 14 / 单臂 7） |
| s_{m,ℓ} | 解码器第 m 层对第 ℓ 层记忆的可学习打分，初始偏向深度对齐层 |

**直觉**：公式没有"记忆更新项"。记忆是常量，梯度只流过 actor 的 1.8–2.7 亿参数；4B VLM 的 key/value 只作为 cross-attention 的读端存在。这也解释了为什么"换记忆"能直接当作因果干预实验（Table 4）——记忆是唯一承载任务身份的通路。

## 4. 工程视角

| 维度 | 数值 / 约束 | 工程含义 |
|------|-------------|----------|
| 稳态在线显存 | 1.22 GiB（RoboTwin）/ 0.86 GiB（LIBERO） | 控制进程本身很轻，可与其他任务共卡 |
| prefill 峰值显存 | 12.11 GiB / 11.74 GiB | 部署的硬门槛在这里，不在稳态；需支持 episode 起点一次性加载 |
| 单 episode 记忆缓存 | 174.6 MiB（RoboTwin，含在 1.22 GiB 内）/ 79.7 MB（LIBERO bf16） | **并发度瓶颈**：100 个并行 episode 就是 ~17 GB 额外缓存 |
| actor 单次调用 | 44.87 ms（RoboTwin）/ 34.25 ms（LIBERO） | 抖动来源单一，且只在 chunk 边界 |
| 首 chunk | 153.74 ms / 122.63 ms | 含 prefill，落在 episode 起点，不在控制路径中段 |
| 测量栈 | PyTorch 2.7.1+cu128，BF16，batch=1，无 torch.compile / TensorRT | 数字**保守**，但也意味着不能与其他已优化部署栈横向比较 |
| 计时协议 | 3 次 warmup + 10 次计时，前后同步，含 resize/normalize/H2D 传输 | 排除了 HTTP 通信开销，属"纯推理函数"口径 |

关键 trade-off：**把延迟从"每 chunk 一次大模型"换成"每 episode 一次大模型 + 每 episode 一份缓存"**。前者是时间成本，后者是空间成本。当并发 episode 数 N 满足 N × 174.6 MiB 逼近显存上限时，这个架构的边际收益会反转——这是论文没有讨论、但部署时一定会撞到的墙。

另一个隐含约束：`⌈H/K⌉` 里的 H 是**执行步数**，不是评测频率。RoboTwin 的 92.43% 是 10,000 次 rollout（50 任务 × 100 episode × Clean/Randomized 两档）汇总，训练则是 200,000 步、batch 256、约 150 accelerator-hours（Table 1）。不要把训练步数和 rollout 步数混为一谈。

## 6. 能力与失败模式

**能做**
- 双臂（RoboTwin，50×14 chunk）与单臂（LIBERO，10×7 chunk）桌面操作，同一套两阶段设计。
- 对 LIBERO-Plus 的视角、背景纹理、光照、物体布局、机器人初始状态、传感器噪声六类扰动均有成功 rollout（Figure 3、Figure 6），其中传感器噪声一例第三人称视图严重损坏仍成功，依赖未扰动的腕部视图。
- 注意力随子目标迁移：300 步 stack_blocks_two 中，控制从左臂转到右臂时头相机注意力从红块转到绿块（Figure 4）——这是"记忆固定但注意力不固定"的定性证据。

**不能做 / 未验证**
- **episode 内任务目标变更**：作者在 Appendix E 明确写"remains unexplored"，只提出可结合事件触发更新与高层重规划作为未来方向。
- **无 action 预训练**：标准 LIBERO 95.95 低于 Faster-WAM (HUST) 的 99.00 与 DM0.5 的 98.50；而 LIBERO-Plus 上落后 π0.5 和 DM0.5，作者归因于这两者使用动作生成权重预训练（Faster-WAM (HUST) 的 Action PT 为 ×，不适用该归因）。
- **长程退化**：94.00 → 90.25，随步数预算增长单调下降。
- **腕部视图是刚需**：去掉腕部视觉跌到 65.60 / 33.49，去掉头视图反而有 92.70 / 74.54——这不是"多视图冗余"，而是"腕部承载闭环反馈"。
- **记忆错配即失效**：同任务不同 episode 的记忆 → 6.26% / 8.36%；不同任务的记忆 → 0.62% / 0.52%。系统对"这份记忆属于这个 episode"的要求是硬的。

### 6.1 隐含假设

1. **任务语义在一个 episode 内平稳**。这是全文的地基，也是唯一的失败边界；论文用 Appendix E 承认而非验证它。
2. **初始多视角帧足以确定任务所需的物体身份与布局**。若关键物体在首帧被遮挡、或需要交互后才显现，记忆里就没有它——而记忆不可更新。
3. **本体状态的变化可以被轻量 actor 吸收，不需要 VLM 重新推理**。支持证据是去掉本体状态只掉 1.65 / 6.70 个百分点（Table 6），说明 actor 对状态的依赖并不算强；但这也可能意味着状态信息利用不足。
4. **摊薄延迟的横向可比性**。各方法 replan 间隔不同（Fast-VLA 50/50，Fast-WAM 32/24，LingBot-VLA 50/25），摊薄口径本身会系统性偏向 chunk 更长、执行更久的方法。

**面试 Tip**：被问到"Fast-VLA 和 VLA-Cache / FAST 有什么本质区别"时，一句话答——**那些方法优化的是"每次调用多贵"，Fast-VLA 优化的是"调用多少次"；它把 backbone 的调用频率从每 chunk 降到每 episode，代价是每 episode 一份不可更新的 KV 缓存和 12 GiB 的 prefill 峰值。**
